# 决议记录

本页记录立项阶段的设计共识；实现进度见[实现状态](implementation-status.md)。不把未提供的授权细节或外部团队排期当作既定事实。每条决议包含决定与理由；背景细节见[架构概念](architecture.md)。

## 法律与许可

| # | 决定 | 理由 |
| --- | --- | --- |
| L1 | 经原作者授权，本项目与 Easybot 无关、独立发展；名称 "EasybotCE" 已获授权 | 明确社区项目独立维护的定位；不推定授权形式与代码复用边界 |
| L2 | 不 fork 原仓库，代码从零实现 | 采用独立实现路线；不对未提供的代码授权条款作推断 |
| L3 | 主程序（Hub）采用 AGPL-3.0-only；MC 侧许可由其团队落地确认 | 保证核心永久开源，防止闭源分叉 |
| L4 | 插件 SDK、示例与协议 Schema 采用 MIT | MIT 降低生态接入门槛；独立进程不构成当然法律豁免，义务取决于实际集成方式 |
| L5 | 贡献采用 DCO，不签 CLA | 降低贡献摩擦 |

## 架构

| # | 决定 | 理由 |
| --- | --- | --- |
| A1 | CE 端点以主动连接 Hub 为主，独立 token 鉴权，支持 wss；OneBot11 正向 WS 为主动连接例外 | NAT/内网 MC 服务器无需开入站端口 |
| A2 | 预留其他未来向外连接扩展，暂不承诺 Hub 联邦 | 拓扑可能演化，先留接口不背实现负担 |
| A3 | 核心模型为"端点 + 绑定 + 功能配置"三层；端点类型 `mc-server` / `chat-bot` / `plugin`；绑定多对多 | 实现"实例为主体、功能为操作"的理念，且 bot 池与服务器实例自由组合 |
| A4 | 插件 = 第三种端点，复用同一 WS 协议；manifest 声明权限范围，Hub 按 token 范围做 API 白名单 | 一个协议 + 一份权限模型即开放生态，无需发明额外插件运行时 |
| A5 | 不兼容 Easybot 原版插件 | 选择新的独立进程插件 API，不承诺旧运行时兼容；不推定授权范围 |
| A6 | CE 协议为 JSON over WebSocket，带版本字段与连接时能力协商；OneBot11 经原生适配 | 可调试、第三方接入门槛低；高频二进制通道留待以后 |
| A7 | 协议语义化版本；Hub 兼容当前及上一代 minor；破坏性变更升 major 并留过渡期 | MC 侧由外部团队开发，版本契约必须明确 |
| A8 | 消息同步规则管线挂在绑定对上：过滤器 → 转换器 → 模板 | 复用端点模型；跨服同步 = 多端点绑定共享规则组 |
| A9 | 命令逐条配置执行身份（控制台 / 指定玩家）与权限回退 | 对应原版"命令身份"能力，且协议需定义相应消息类型 |

## v1 范围

| # | 决定 | 理由 |
| --- | --- | --- |
| S1 | v1 交付八项功能：双向消息同步、账号绑定管理、自定义命令、黑白名单、AI 对接、占位符/变量系统、图片模板（rod 渲染）、跨服消息同步 | 后续还有功能补充，第一版必须形成完整闭环 |
| S2 | 游戏内图片 GUI 渲染以 v1.1 为协调目标；MC 团队先对接 WS 通道 + 消息/命令桥 | MC 侧工作量失控风险 |
| S3 | 账号绑定状态机六项进 v1：验证码模式、信任模式、强制绑定拦截、解绑、退群自动解绑、群名片同步 | 绑定功能的最小完整闭环 |
| S4 | MC 侧客户端由另一团队开发，本项目只交付对接文档 + CLI 参考模拟器 | 团队分工明确；模拟器兼作协议一致性测试夹具 |
| S5 | BOT 端 v1 仅支持 OneBot11（正向 + 反向 WS）；Milky、Telegram 排 v1.1 | OneBot11 是国内 MC 社区主流，先做深再做宽 |
| S6 | AI 对接为通用 OpenAI 兼容接口（base URL + key + model），SiliconFlow/DeepSeek 等为预置模板 | 不绑定厂商，扩展零成本 |
| S7 | 图片模板内嵌 rod 驱动启动无头浏览器，不分 full/lite 档 | 对应原版 FULL 版能力；Chromium 是独立子进程，不要求独立 sidecar 服务 |

## 技术栈与数据

| # | 决定 | 理由 |
| --- | --- | --- |
| T1 | Go 1.27；模块路径 `github.com/EasybotCE/easybotce`；monorepo（`cmd/hub`、`internal/`、`docs/`） | 仓库级模块路径才能被他人引用 |
| T2 | 数据访问层用 sqlc，SQL 透明可审计 | AGPL 项目长期社区维护，SQL 透明比开发速度重要 |
| T3 | 数据库：SQLite 为主（modernc.org/sqlite，免 CGO），兼容 MySQL、PostgreSQL | 单二进制分发友好，同时满足大型部署 |
| T4 | 数据库是配置唯一真源；业务 YAML/JSON 仅导入导出，引导配置例外；API 改配置即时生效 | 接口先行，避免文件/DB 双源冲突 |
| T5 | 消息日志默认不落库，可配置开启 + 留存天数 | 隐私与库体积 |
| T6 | LiteDB 迁移用 C# dotnet tool sidecar 导出 JSON，Hub `import` 命令导入；范围为绑定 + 配置，不含插件数据 | Go 生态无成熟 LiteDB 读取库，原生解析是数周级高风险工作 |
| T7 | 交付形态：单静态二进制 + Docker；引导配置 = 环境变量 + 最小 YAML；slog 结构化日志；预留 `/metrics` | 部署简单，可观测性留口子 |
| T8 | Web UI 暂缓，接口先行：OpenAPI 3.1 规范随仓库提交并生成文档；`/v1` 前缀；Bearer token；WS 事件流支持按端点/类型过滤订阅；管理操作全 API 化 | 杜绝"UI 补丁式 API"，规范即产品 |

| # | 决定 | 理由 |
| --- | --- | --- |
| E1 | SDK 独立仓库 `github.com/EasybotCE/sdk`；语言顺序 TypeScript → Go；内容 = 协议类型 + WS 客户端 + manifest 工具 | TS 覆盖原社区 JS 习惯与 Web 生态 |

| E3 | CI 基线：GitHub Actions 跑单测、sqlc 生成校验、SQLite/MySQL/PG 三库矩阵集成测试（testcontainers）、协议一致性测试（模拟器） | 多库支持与外部团队对接都要自动化验证 |
